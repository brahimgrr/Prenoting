# Prenoting Deep Dive Report

This report explains the project from three angles:

1. The PHP and Laravel ideas you need in order to read it.
2. The exact architecture of this codebase.
3. The main business workflows, traced through routes, controllers, models, services, views, assets, database tables, and tests.

The project is a Laravel Blade medical appointment portal called MedPortal. It is a single-doctor dermatology booking system where:

- guests see a landing page and can log in or register;
- patients can register, book appointments, view appointments, cancel, reschedule, and edit contact/password data;
- the doctor can view the agenda, create/block/unblock availability, manage treatments, and edit contact data;
- an admin can access a simple admin dashboard with a phpMyAdmin link.

The stack is declared in `composer.json`, `package.json`, and `README.md`: PHP 8.4, Laravel 13, MySQL 8.4, Blade templates, Eloquent, Bootstrap 5, jQuery, and Vite.

## 1. The Request Lifecycle

When a browser visits the app, the request flows like this:

1. The web server points all public traffic at `public/index.php`.
2. `public/index.php` loads `vendor/autoload.php`, which is Composer's autoloader.
3. `public/index.php` loads `bootstrap/app.php`.
4. `bootstrap/app.php` creates the Laravel application, registers `routes/web.php`, registers console commands, registers the health route `/up`, and creates the `role` middleware alias.
5. Laravel captures the HTTP request and matches it against `routes/web.php`.
6. Middleware runs before the controller. In this project, `auth`, `guest`, and custom `role` middleware are especially important.
7. The controller method receives an `Illuminate\Http\Request`, validates input, queries models, calls services, and returns a redirect, JSON response, or Blade view.
8. Eloquent models translate PHP objects into database rows.
9. Blade templates in `resources/views` render HTML.
10. Vite injects `resources/css/app.css` and `resources/js/app.js`.
11. Laravel returns the final HTTP response.

The command-line lifecycle is similar, but starts from `artisan` instead of `public/index.php`. `artisan` loads the same application and handles console commands such as `php artisan migrate`, `php artisan route:list`, and `php artisan serve`.

## 1A. Core Web Development Concepts

Before Laravel, PHP, or JavaScript, this project is a web application. Web applications are conversations between a browser and a server.

The browser sends an HTTP request:

```text
GET /patient/book?service_id=3 HTTP/1.1
Host: 127.0.0.1:8080
Cookie: medportal_session=...
```

The server returns an HTTP response:

```text
HTTP/1.1 200 OK
Content-Type: text/html

<!doctype html>
<html lang="it">
...
```

The main HTTP methods in this app are:

- `GET`: read a page or endpoint. Example: `GET /patient/book` shows the booking page.
- `POST`: create or trigger an action. Example: `POST /appointments` creates an appointment.
- `PATCH`: partially update an existing thing. Example: `PATCH /patient/profile` updates contact data.
- `PUT`: replace/update a thing. Example: `PUT /patient/password` updates the password.
- `DELETE`: delete or disable a thing. Example: `DELETE /doctor/treatments/{service}` disables a treatment.

Browsers only support `GET` and `POST` directly in normal HTML forms. Laravel solves this with method spoofing. In Blade you will see:

```blade
<form method="POST" action="/patient/profile">
  @csrf
  @method('PATCH')
  ...
</form>
```

The actual browser request is still `POST`, but Laravel reads the hidden `_method=PATCH` field generated by `@method('PATCH')` and treats it as a `PATCH` route.

Query strings carry temporary UI state. In this app:

```text
/patient/book?service_id=3&week_start=2030-05-02&date=2030-05-02&slot_id=15#booking-confirm
```

Means:

- `service_id=3`: selected medical service.
- `week_start=2030-05-02`: the visible five-day availability strip starts here.
- `date=2030-05-02`: selected day.
- `slot_id=15`: selected time slot.
- `#booking-confirm`: browser should jump to the confirmation section.

Sessions keep login state. HTTP itself is stateless: every request is independent. Laravel keeps the user logged in by storing a session ID in a cookie and storing session data server-side. This project uses the database session driver in `config/session.php`, so production/local sessions are stored in the `sessions` table. In tests, `phpunit.xml` sets `SESSION_DRIVER=array`, so sessions live only in memory during the test.

Redirects are a normal web pattern. After successful form submission, the app often returns a redirect instead of rendering a page directly:

```php
return redirect('/patient/appointments')->with('status', 'Appuntamento confermato.');
```

That implements the "POST/Redirect/GET" pattern:

1. Browser submits a POST.
2. Server changes data.
3. Server redirects to a GET page.
4. Refreshing the page does not submit the form again.

HTML, CSS, and JavaScript divide frontend responsibilities:

- HTML gives structure: forms, buttons, links, sections, lists.
- CSS gives presentation: layout, spacing, colors, responsive behavior.
- JavaScript adds behavior in the browser: fetch partials, update visible slots, open modals, move the agenda marker.

This project is server-rendered first. That means Laravel returns complete HTML pages. JavaScript enhances them, but most important workflows still work as normal links and forms if JavaScript fails.

## 2. PHP Concepts Used Here

PHP files start with `<?php`. Laravel code is organized with namespaces. For example, `App\Http\Controllers\AuthController` means the file belongs to the `App\Http\Controllers` namespace. Composer maps the `App\` namespace to the `app/` directory using PSR-4 autoloading in `composer.json`.

Classes are the core unit of application code:

- `class User extends Authenticatable` means `User` inherits login behavior from Laravel's auth base class.
- `use HasFactory; use Notifiable;` inside a class imports traits, which are reusable bundles of methods.
- `public`, `private`, and `protected` control visibility.
- `public function login(Request $request): RedirectResponse` says the method accepts a `Request` and returns a redirect.

Common PHP syntax in this app:

- Arrays: `['username' => 'required']` and nested arrays are used heavily for validation and config.
- Closures: `fn ($query) => ...` is a short anonymous function, often used to conditionally modify queries.
- Constants: `User::ROLE_PATIENT` and `Appointment::STATUS_CONFIRMED` avoid repeated magic strings.
- Static methods: `CodiceFiscaleService::calcola(...)` is called without creating an object.
- Null-safe operator: `$appointment->service?->name` means "if service exists, read name, otherwise return null."
- Match expressions: `match ($this->role) { ... }` is a stricter switch-like expression.
- Exceptions: `throw ValidationException::withMessages(...)` interrupts the request and returns validation errors to the previous page.

Laravel adds its own conventions:

- Facades such as `Auth`, `DB`, `Hash`, `Route`, and `Schema` are static-looking access points to framework services.
- Collections, returned by methods such as `get()` and `collect()`, provide fluent methods like `map`, `filter`, `values`, `groupBy`, and `sortBy`.
- Carbon objects represent dates and times. This code uses `CarbonImmutable` for many scheduling calculations.

### PHP Variables, Types, And Return Types

Variables in PHP start with `$`. Examples from the app:

```php
$user = auth()->user();
$role = $user?->portalRole();
$selectedDate = (string) $request->query('date', now()->toDateString());
```

PHP is dynamically typed, but this code often uses type hints for clarity and safety:

```php
public function login(Request $request): RedirectResponse
```

That means:

- `$request` must be an instance of `Illuminate\Http\Request`;
- the method promises to return `Illuminate\Http\RedirectResponse`.

Private helper methods are also typed:

```php
private function resolveSelectedPeriod(Request $request): string
```

This style makes controller code easier to reason about. You can tell what a method needs and what it returns without reading every line.

### Namespaces And Imports

At the top of `AuthController.php`, you see:

```php
namespace App\Http\Controllers;

use App\Models\PatientProfile;
use App\Models\User;
use App\Services\CodiceFiscaleService;
use Illuminate\Http\Request;
```

The namespace says "this class lives in the controller area." The `use` statements import other classes so the file can write `User` instead of `App\Models\User`.

Composer autoloading connects names to files. In `composer.json`:

```json
"psr-4": {
  "App\\": "app/"
}
```

So `App\Services\AppointmentService` maps to `app/Services/AppointmentService.php`.

### Classes, Inheritance, And Traits

`app/Models/User.php` starts like this:

```php
class User extends Authenticatable
{
  use HasFactory;
  use Notifiable;
```

This says:

- `User` is a class.
- It extends Laravel's `Authenticatable`, so Laravel can log it in.
- It uses traits: `HasFactory` for test/model factories, `Notifiable` for notifications.

The class also declares constants:

```php
public const ROLE_ADMIN = 'admin';
public const ROLE_DOCTOR = 'doctor';
public const ROLE_PATIENT = 'patient';
```

Using constants is safer than writing strings everywhere. If you mistype `'patinet'`, PHP will not know. If you mistype `User::ROLE_PATINET`, PHP will fail loudly.

### Arrays As Configuration And Data

PHP arrays can act like lists:

```php
[
  Appointment::STATUS_CONFIRMED,
  Appointment::STATUS_CHECKED_IN,
]
```

Or dictionaries:

```php
[
  'username' => ['required', 'email', 'max:150', 'unique:users,username'],
  'password' => ['required', 'string', 'min:8', 'confirmed'],
]
```

Laravel uses arrays heavily for validation, configuration, route data, and view data.

In `BookingController@show`, the controller passes an associative array to a Blade view:

```php
return view('patient.booking', [
  'services' => MedicalService::where('is_active', true)->orderBy('name')->get(),
  'selectedService' => $selectedService,
  'selectedDate' => $selectedDate,
  'selectedSlot' => $selectedSlot,

```

Inside Blade, those keys become variables:

```blade
@if ($selectedService)
  ...
@endif
```

### Closures, Arrow Functions, And Fluent Code

Modern PHP supports short closures:

```php
fn (Appointment $appointment) => $appointment->start_at->isFuture()
```

This codebase uses them with Eloquent and Collections:

```php
$upcoming = $appointments
  ->filter(fn (Appointment $appointment) => in_array($appointment->status, Appointment::ACTIVE_SLOT_STATUSES, true) && $appointment->start_at->isFuture())
  ->sortBy('start_at')
  ->values();
```

Read this as a pipeline:

1. Start with all appointments.
2. Keep only active future appointments.
3. Sort them by start time.
4. Reindex the collection.

The same style appears in query builders:

```php
MedicalService::query()
  ->where('is_active', true)
  ->when($validated['search'] ?? null, fn ($query, $search) => $query->where('name', 'like', "%{$search}%"))
  ->orderBy('name')
  ->get();
```

`when` means "only apply this condition if the value exists."

### Null Safety

The null-safe operator `?->` is everywhere in views:

```blade
{{ $appointment->service?->name ?? 'Appuntamento' }}
```

That means:

- if `$appointment->service` exists, read its `name`;
- if it is null, the expression becomes null;
- then `?? 'Appuntamento'` provides a fallback.

This matters because real data can be incomplete. The UI should not crash just because a related row is missing.

### Match Expressions

`User::portalRole()` uses `match`:

```php
return match ($this->role) {
  self::ROLE_ADMIN => self::ROLE_ADMIN,
  self::ROLE_DOCTOR => self::ROLE_DOCTOR,
  self::ROLE_PATIENT => self::ROLE_PATIENT,
  default => self::ROLE_USER,
};
```

This normalizes roles. If the database contains an unexpected role, the app treats it as `user`, which has no portal route.

### Exceptions And Validation Errors

Laravel validation usually looks like:

```php
$validated = $request->validate([
  'slot_id' => ['required', 'integer', 'exists:availability_slots,id'],
  'service_id' => ['required', 'integer', 'exists:medical_services,id'],
]);
```

If validation fails, Laravel automatically:

1. redirects back;
2. stores errors in the session;
3. stores old input;
4. makes `$errors` available in Blade.

Sometimes the app throws custom validation errors:

```php
throw ValidationException::withMessages([
  'slot_id' => 'Questo orario non e piu disponibile.',
]);
```

That gives the same user experience as normal validation, but the rule can depend on business logic.

### Static Service Methods Vs Injectable Services

`CodiceFiscaleService::calcola(...)` is static because it is a pure calculation. It receives inputs and returns a string.

`AppointmentService` is injected into controllers:

```php
public function store(Request $request, AppointmentService $appointments): RedirectResponse
```

Laravel's service container sees the `AppointmentService` type hint and creates one automatically. This is dependency injection. It keeps controllers from manually constructing dependencies.

Use this mental rule:

- pure utility calculation -> static method can be fine;
- operation with database transactions and domain rules -> injectable service is better.

### Dates With Carbon

Laravel uses Carbon for dates. In this project, scheduling logic often uses `CarbonImmutable`:

```php
$start = CarbonImmutable::parse("{$validated['date']} {$validated['start_time']}:00");
$end = CarbonImmutable::parse("{$validated['date']} {$validated['end_time']}:00");
```

Immutable means methods return new objects instead of changing the original object. That reduces subtle date bugs.

Examples:

```php
$selectedDay = CarbonImmutable::parse($selectedDate)->startOfDay();
$nextDayUrl = request()->fullUrlWithQuery(['date' => $selectedDay->addDay()->toDateString()]);
```

`addDay()` returns a new date, leaving `$selectedDay` conceptually stable.

## 3. Laravel Concepts In This Project

Routing: `routes/web.php` maps HTTP verbs and URLs to controller methods. Example: `POST /appointments` goes to `BookingController@store`.

Middleware: middleware protects or transforms requests. `auth` requires a logged-in user. `guest` keeps logged-in users away from login/register pages. The custom `role` middleware checks that the logged-in user has the right portal role.

Controllers: controllers are HTTP coordinators. They validate input, call models/services, and choose the response. They should not usually contain the deepest business invariants.

Services: `AppointmentService` holds the strongest appointment business rules. This is a good pattern because booking, canceling, rescheduling, and status changes can be reused safely.

Models: Eloquent models represent tables. `Appointment`, `AvailabilitySlot`, `MedicalService`, `PatientProfile`, `DoctorProfile`, and `User` are the domain objects.

Migrations: files in `database/migrations` define database structure over time. They are versioned schema changes.

Seeders: `database/seeders/DatabaseSeeder.php` creates demo users, treatments, doctor profile, and future availability slots.

Blade: `.blade.php` files are server-rendered templates. They mix HTML with Blade directives such as `@extends`, `@section`, `@foreach`, `@csrf`, `@method`, `@error`, and `@include`.

Vite: `vite.config.js` connects Laravel to frontend assets. `@vite(['resources/css/app.css', 'resources/js/app.js'])` in the layouts includes the compiled CSS and JS.

Testing: feature tests in `tests/Feature` simulate real HTTP requests and assert redirects, HTML content, JSON, database rows, and security behavior.

Generated files: `bootstrap/cache/services.php` is generated framework cache. Do not edit it directly. The source files are in `app`, `routes`, `resources`, `database`, `config`, and `tests`.

### MVC In This Codebase

Laravel is commonly described as MVC:

- Model: represents data and database rules. Example: `Appointment`.
- View: renders HTML. Example: `patient.booking`.
- Controller: handles a request. Example: `BookingController@store`.

But real Laravel apps often add a fourth layer:

- Service: holds important business operations. Example: `AppointmentService`.

For this app, the flow is:

```text
Route -> Middleware -> Controller -> Service -> Model -> Database
                                      |
                                      v
                                   View/Redirect/JSON
```

Example for booking:

```text
POST /appointments
  -> auth + patient role middleware
  -> BookingController@store
  -> AppointmentService::book
  -> AvailabilitySlot + MedicalService + Appointment models
  -> MySQL transaction
  -> redirect /patient/appointments
```

### Routes In Detail

A route can return a closure:

```php
Route::get('/', function () {
  ...
})->name('home');
```

Or point to a controller:

```php
Route::post('/appointments', [BookingController::class, 'store']);
```

The controller version means:

- when a `POST` request arrives at `/appointments`;
- instantiate or resolve `BookingController`;
- call its `store` method.

Route groups avoid repetition:

```php
Route::middleware('auth')->group(function (): void {
  Route::middleware('role:'.User::ROLE_PATIENT)->group(function (): void {
    Route::get('/patient/book', [BookingController::class, 'show']);
  });
});
```

All routes inside the outer group require login. All routes inside the patient group also require patient role.

### Route Model Binding

Routes like this:

```php
Route::get('/appointments/{appointment}/edit', [PatientAppointmentController::class, 'edit']);
```

Match URLs like:

```text
/appointments/42/edit
```

Because the controller method is:

```php
public function edit(Request $request, Appointment $appointment): View
```

Laravel automatically runs roughly:

```php
$appointment = Appointment::findOrFail(42);
```

This is convenient, but it is not authorization. The controller still calls:

```php
$this->authorizePatientAppointment($request, $appointment);
```

That prevents patient A from editing patient B's appointment.

### Middleware In Detail

`bootstrap/app.php` registers the custom middleware alias:

```php
$middleware->alias([
  'role' => EnsureRole::class,
]);
```

Then routes can use:

```php
->middleware('role:'.User::ROLE_DOCTOR)
```

`EnsureRole` receives the current request, a `$next` callback, and allowed roles:

```php
public function handle(Request $request, Closure $next, string ...$roles): Response
{
  $user = $request->user();

  if (! $user || ! in_array($user->portalRole(), $roles, true)) {
    abort(403);
  }

  return $next($request);
}
```

Read this as:

1. Get current user from session.
2. If no user or role is not allowed, stop with 403.
3. Otherwise pass the request to the next middleware/controller.

### Controllers In Detail

Controllers in this project usually follow this shape:

```php
public function someAction(Request $request): RedirectResponse|View|JsonResponse
{
  $validated = $request->validate([...]);
  $models = Model::query()->...->get();
  return view('some.view', [...]);
}
```

The controller's job is not "do everything." Its job is to coordinate:

- read input;
- validate input;
- call domain logic;
- choose response.

For example, `BookingController@store` does not manually set appointment fields and slot fields. It validates HTTP input, then delegates to `AppointmentService`.

### Eloquent Models In Detail

Eloquent gives each table a PHP class.

`AvailabilitySlot`:

```php
class AvailabilitySlot extends Model
{
  protected $fillable = [
    'start_at',
    'end_at',
    'is_blocked',
    'is_booked',
  ];
```

`$fillable` protects against mass assignment. It tells Laravel which fields can be passed into `create()` or `update()`.

Example:

```php
AvailabilitySlot::create([
  'start_at' => $start,
  'end_at' => $end,
]);
```

Only fields in `$fillable` are allowed.

Casts convert database strings/integers into useful PHP values:

```php
protected function casts(): array
{
  return [
    'start_at' => 'datetime',
    'end_at' => 'datetime',
    'is_blocked' => 'boolean',
    'is_booked' => 'boolean',
  ];
}
```

Because of this, `$slot->start_at` is a Carbon date object, and `$slot->is_blocked` behaves like a boolean.

### Relationships In Detail

In `Appointment.php`:

```php
public function service(): BelongsTo
{
  return $this->belongsTo(MedicalService::class, 'service_id');
}
```

This means every appointment references one row in `medical_services` through `appointments.service_id`.

In Blade:

```blade
{{ $appointment->service?->name ?? 'Appuntamento' }}
```

This reads the related service's name.

`withPortalRelations()` eager-loads common relationships:

```php
public function scopeWithPortalRelations(Builder $query): Builder
{
  return $query->with(['patient.user', 'service', 'slot']);
}
```

Without eager loading, a loop over appointments could trigger one extra query per appointment for patient, service, and slot. That is the classic N+1 query problem. Eager loading says: load these relations up front in fewer queries.

### Query Builder And Scopes

A query like this:

```php
Appointment::withPortalRelations()
  ->where('patient_id', $request->user()->patientProfile->id)
  ->orderByDesc('start_at')
  ->get();
```

Means:

1. Start an appointment query.
2. Include common portal relations.
3. Restrict to this patient.
4. Sort newest first.
5. Execute with `get()`.

Until `get()`, `first()`, `exists()`, `count()`, or similar is called, Laravel is building SQL but has not executed it yet.

Model scopes make reusable query fragments:

```php
public function scopePublicAvailable(Builder $query): Builder
{
  return $query
    ->where('is_blocked', false)
    ->where('is_booked', false)
    ->where('start_at', '>', now());
}
```

Laravel lets you call that as:

```php
AvailabilitySlot::query()->publicAvailable()->get();
```

### Transactions And Locks

The most advanced Laravel/database concept in this app is transactional booking.

`AppointmentService::book` uses:

```php
return DB::transaction(function () use ($patient, $slotId, $serviceId, $notes): Appointment {
  $slot = AvailabilitySlot::lockForUpdate()->findOrFail($slotId);
  ...
});
```

A transaction means:

- all database changes inside succeed together;
- or all changes are rolled back if something fails.

`lockForUpdate()` means the selected slot row is locked until the transaction finishes. That protects against two patients booking the same slot at the same time.

Imagine two requests arrive together:

```text
Patient A -> book slot 10
Patient B -> book slot 10
```

Without locking, both might read "not booked" before either writes. With locking:

1. Patient A locks the slot.
2. Patient B waits.
3. Patient A creates appointment and marks slot booked.
4. Patient B reads the now-booked slot and gets validation error.

### Validation Rules

Laravel validation rules can check shape and database existence:

```php
'slot_id' => ['required', 'integer', 'exists:availability_slots,id']
```

Means:

- field must be present;
- it must be an integer;
- it must match an existing `availability_slots.id`.

Business validation is separate:

```php
if ($slot->is_blocked || $slot->is_booked || $slot->start_at->isPast()) {
  $errors['slot_id'] = 'Questo orario non e piu disponibile.';
}
```

This distinction is important:

- request validation: "does the submitted data look valid?"
- domain validation: "is this action allowed right now?"

## 5. Domain Model

The current domain is intentionally simplified to one doctor. That is why appointments and availability slots no longer store `doctor_id` or `clinic_id`.

Main tables:

- `users`: authentication account. Stores username, email, names, password, and role.
- `patient_profiles`: patient-specific data: birth date, place of birth, gender, phone, address, codice fiscale.
- `doctor_profiles`: doctor-specific data: display name, bio, license number, phone, clinic address, active flag.
- `medical_services`: treatments/prestations patients can book. Categories are `VISITA` or `ESAME`.
- `availability_slots`: global future slots for the single doctor. A slot has start/end times and can be blocked or booked.
- `appointments`: patient booking for a service and slot, with copied start/end times, status, notes, and cancellation reason.
- `appointment_status_history`: audit trail for status changes, cancellations, and reschedules.

Relationships:

- `User` has one `PatientProfile`.
- `User` has one `DoctorProfile`.
- `PatientProfile` has many `Appointment` records.
- `Appointment` belongs to `PatientProfile`, `MedicalService`, and `AvailabilitySlot`.
- `AvailabilitySlot` has many `Appointment` records, though business rules aim for only one active appointment per slot.
- `Appointment` has many `AppointmentStatusHistory` rows.

Important model details:

- `User` casts passwords as `hashed`, so assigning a plain password is automatically hashed by Laravel.
- `Appointment::ACTIVE_SLOT_STATUSES` is `confirmed` and `checked_in`; those statuses keep a slot occupied.
- `AvailabilitySlot::scopePublicAvailable()` filters to future, not blocked, not booked slots.
- `Appointment::scopeWithPortalRelations()` eager-loads `patient.user`, `service`, and `slot` to avoid repetitive database queries in portal views.

## 8. Patient Booking Workflow

The booking screen starts at `GET /patient/book`, handled by `BookingController@show`.

The user chooses:

1. a service;
2. a visible available date;
3. an available time slot;
4. confirmation with optional notes.

`BookingController` builds view state:

- active services;
- selected service;
- selected slot;
- selected period filter: all, morning, afternoon;
- available dates;
- five visible available days at a time;
- slots grouped by day;
- URLs for the non-reload week partial.

`resources/views/patient/partials/booking-wizard.blade.php` renders the three-step wizard.

`resources/views/patient/partials/booking-week-partial.blade.php` renders the five-day strip and slot buttons.

`resources/js/app.js` intercepts week arrow clicks with `fetch`, updates `#booking-week-region`, and pushes the new URL into browser history. If fetch fails, it falls back to normal navigation.

When the user submits the booking form, `POST /appointments` calls `BookingController@store`, which validates `slot_id`, `service_id`, and notes, then calls `AppointmentService::book`.

`AppointmentService::book` is the key safety point:

- starts a database transaction;
- locks the selected slot with `lockForUpdate()`;
- loads the service;
- validates the service and slot;
- creates the appointment;
- marks the slot as booked;
- returns the appointment with relations loaded.

The slot lock matters because two users might try to book the same time at the same moment. Locking turns that race into a safe serialized operation.

### Booking Workflow With Concrete Files

The booking workflow is a good way to understand the whole stack.

Step 1: route.

```php
Route::get('/patient/book', [BookingController::class, 'show']);
Route::post('/appointments', [BookingController::class, 'store']);
```

The `GET` route displays the form. The `POST` route performs the booking.

Step 2: controller builds page state.

`BookingController@show` reads query parameters:

```php
$selectedService = $request->integer('service_id')
  ? MedicalService::where('is_active', true)->find($request->integer('service_id'))
  : null;
```

This means:

- if the URL has `service_id`, try to load that active service;
- if there is no service selected yet, use `null`.

It also calculates:

- `$selectedSlot`
- `$selectedPeriod`
- `$allAvailableDates`
- `$weekStart`
- `$weekDays`
- `$weekSlots`

That is a common controller pattern: convert raw request state into clean view state.

Step 3: Blade renders the wizard.

`patient.booking` contains:

```blade
@include('patient.partials.booking-wizard', ['isReschedule' => false])
```

The partial checks the state:

```blade
@if ($selectedService)
  <div id="booking-week-region">
    @include('patient.partials.booking-week-partial')
  </div>
@endif
```

So the date/time section appears only after a service is selected.

Step 4: links carry state.

When the user clicks a service card, the app navigates to a URL with `service_id`:

```text
/patient/book?service_id=3#booking-step-day
```

When the user clicks a slot, it navigates to a URL with `slot_id`:

```text
/patient/book?service_id=3&week_start=2030-05-02&date=2030-05-02&slot_id=15#booking-confirm
```

This means the UI state is shareable and reload-safe. A browser refresh does not lose the selected service/day/slot because the URL contains that state.

Step 5: confirmation form submits.

The confirmation form posts:

```blade
<form method="POST" action="{{ $formAction }}" class="booking-confirm-form">
  @csrf
  <input type="hidden" name="service_id" value="{{ $selectedService->id }}">
  <input type="hidden" name="slot_id" value="{{ $selectedSlot->id }}">
  <button type="submit" class="btn btn-primary">Conferma prenotazione</button>
</form>
```

Hidden inputs send selected IDs to the server. The user sees meaningful labels, but the server receives stable database identifiers.

Step 6: service enforces invariants.

`BookingController@store` calls:

```php
$appointments->book(
  $request->user()->patientProfile,
  (int) $validated['slot_id'],
  (int) $validated['service_id'],
  $validated['notes'] ?? '',
);
```

The controller does not decide whether the slot is truly available. `AppointmentService` does.

### Why Booking Uses Both `appointments` And `availability_slots`

At first it may look redundant that appointment time is saved twice:

- `availability_slots.start_at`
- `appointments.start_at`

This is intentional. The slot is the bookable resource. The appointment is the historical event. Copying start/end onto the appointment means the appointment still has its own time even if slot logic changes later.

The important consistency rule is:

- confirmed or checked-in appointment -> slot should be booked;
- cancelled future appointment -> slot should be freed;
- reschedule -> old slot freed, new slot booked.

That rule is centralized in `AppointmentService`.

### DOM Selection

The JavaScript often starts by finding elements:

```js

```

`document.querySelector` finds the first matching element. Attribute selectors like `[data-agenda-scroll-container]` are a clean pattern: JavaScript hooks are stored in `data-*` attributes instead of depending on CSS classes that might change for styling reasons.

The optional chaining operator `?.` in JavaScript works like PHP's null-safe operator. If `container` is null, `container?.querySelector(...)` returns undefined instead of crashing.

### Event Listeners And Event Delegation

Instead of adding click handlers to every individual button, this project uses event delegation:

```js
document.addEventListener("click", (e) => {
  const arrow = e.target.closest("[data-week-url]");
  ...
});
```

This means:

1. Listen for all clicks on the document.
2. Ask whether the clicked element or one of its ancestors matches `[data-week-url]`.
3. If yes, handle it as a week navigation click.

This is useful because the booking week HTML can be replaced after a fetch. Newly inserted elements still work because the listener is on `document`, not on the old elements.

### Fetch And Partial Page Updates

The booking week arrows are real links in Blade. JavaScript enhances them:

```js
fetch(weekUrl, { headers: { "X-Requested-With": "XMLHttpRequest" } })
  .then((res) => {
    if (!res.ok) throw new Error();
    return res.text();
  })
  .then((html) => {
    region.innerHTML = html;
    history.pushState({}, "", pageUrl);
  })
  .catch(() => {
    window.location.href = pageUrl;
  });
```

This is the browser equivalent of saying:

1. Request only the week partial.
2. If the response is OK, read it as HTML text.
3. Replace `#booking-week-region` with the returned HTML.
4. Update the browser URL without a full reload.
5. If anything fails, navigate normally.

This is progressive enhancement done well. The HTML contains working `href` links, and JavaScript upgrades them into a smoother interaction.

### Browser History

`history.pushState({}, "", pageUrl)` updates the address bar without reloading. The app uses this after fetch navigation and day selection so the URL still reflects the current booking state.

Why that matters:

- refresh keeps the same selected state;
- browser back/forward is more meaningful;
- copied URLs are closer to the current UI state.

### Migrations In Detail

A migration is PHP code that changes the database schema.

Example from the initial domain migration:

```php
Schema::create('users', function (Blueprint $table): void {
  $table->id();
  $table->string('username')->unique();
  $table->string('email')->nullable()->index();
  $table->string('password');
  $table->string('role', 32)->default(User::ROLE_PATIENT)->index();
  $table->rememberToken();
  $table->timestamps();
});
```

This creates:

- an auto-incrementing primary key with `$table->id()`;
- string columns;
- a unique constraint on username;
- indexes for faster lookup;
- a remember token for "remember me" auth support;
- `created_at` and `updated_at` timestamps.

Foreign keys define relationships at the database level:

```php
$table->foreignId('user_id')->unique()->constrained()->cascadeOnDelete();
```

This means:

- create a `user_id` column;
- make it unique, so each user has at most one patient profile;
- reference the `users` table by convention;
- delete the patient profile if the user is deleted.

`restrictOnDelete()` is different:

```php
$table->foreignId('service_id')->constrained('medical_services')->restrictOnDelete();
```

This prevents deleting a service while appointments still reference it. That is why the doctor treatment delete action sets `is_active=false` instead of actually deleting the row.

### Why Later Migrations Modify Earlier Design

Laravel migrations are chronological. The current schema is the result of all migrations, not just the first one.

The first domain migration included:

- specialties;
- clinic locations;
- doctor-service many-to-many table;
- doctor/clinic foreign keys on slots and appointments.

Later, `2026_04_30_000001_simplify_single_doctor_domain.php` removed much of that because the app became a single-doctor product.

That is normal. Migrations are a history of product decisions. You should read them as "how the database evolved," not as one perfect final schema file.

### Seeders In Detail

`DatabaseSeeder` creates demo data:

```php
$doctorUser = User::updateOrCreate(
  ['username' => 'doctor.derm'],
  [
    'email' => 'doctor.derm@example.com',
    'first_name' => 'Kylian',
    'last_name' => 'Mbappe',
    'role' => User::ROLE_DOCTOR,
    'password' => Hash::make('doctor123'),
  ],
);
```

`updateOrCreate` means:

1. Find a user where `username = doctor.derm`.
2. If it exists, update it with the second array.
3. If it does not exist, create it.

That makes seeders repeatable. Running `php artisan migrate --seed` multiple times should not create duplicate demo users.

Seeder slots:

```php
$base = CarbonImmutable::now()->setTime(9, 0, 0);
foreach (range(1, 7) as $dayOffset) {
  foreach (range(0, 2) as $hourOffset) {
    $startAt = $base->addDays($dayOffset)->addHours($hourOffset);
    AvailabilitySlot::updateOrCreate(
      ['start_at' => $startAt],
      [
        'end_at' => $startAt->addMinutes(30),
        'is_blocked' => false,
        'is_booked' => false,
      ],
    );
  }
}
```

This creates demo availability for the next week. Because it uses `start_at` as the lookup key, re-running seeds updates existing matching slots instead of duplicating them.

### SQL Mental Model Behind Eloquent

Eloquent code:

```php
MedicalService::where('is_active', true)->orderBy('name')->get()
```

Rough SQL equivalent:

```sql
select * from medical_services
where is_active = 1
order by name asc;
```

Eloquent code:

```php
AvailabilitySlot::query()
  ->where('start_at', '<', $end)
  ->where('end_at', '>', $start)
  ->exists();
```

Rough SQL equivalent:

```sql
select exists(
  select 1 from availability_slots
  where start_at < :end
    and end_at > :start
);
```

Learning Laravel is easier if you remember that Eloquent is building SQL. You are not escaping the database; you are using a PHP API to express database operations.

## 15. Security And Consistency

Important protections:

- Session auth uses Laravel's `web` guard.
- CSRF tokens protect forms through `@csrf`.
- Role middleware protects patient, doctor, and admin areas.
- Patient appointment ownership is manually checked before edit/cancel/reschedule.
- Passwords are hashed.
- Request validation rejects malformed input.
- Booking/cancel/reschedule operations use transactions.
- Slot booking uses row locks to prevent double booking.
- Appointment history records significant state changes.

Things to remember while changing the app:

- Do not trust route model binding alone for ownership. It loads by ID; you still need a patient/doctor authorization rule.
- Do not update slot `is_booked` separately from appointment creation/cancel/reschedule. Use `AppointmentService`.
- Do not edit generated cache files such as `bootstrap/cache/services.php`.
- Do not remove inactive treatments if old appointments still reference them.

### Security Concepts With Codebase Examples

Authentication answers: "Who are you?"

In this project:

```php
Auth::login($user);
$request->session()->regenerate();
```

`Auth::login` stores the user's identity in the session. `session()->regenerate()` prevents session fixation by issuing a fresh session ID after login.

Authorization answers: "Are you allowed to do this?"

Role authorization:

```php
Route::middleware('role:'.User::ROLE_DOCTOR)->group(...)
```

Ownership authorization:

```php
abort_unless($appointment->patient_id === $request->user()->patientProfile->id, 404);
```

Both are necessary. A user can have the patient role but still not own a particular appointment.

CSRF protection answers: "Did this form come from this app?"

Every mutating form includes:

```blade
@csrf
```

Laravel rejects missing or invalid CSRF tokens.

Input validation answers: "Is this input shaped correctly?"

```php
'date' => ['required', 'date_format:Y-m-d']
```

Business validation answers: "Is this operation allowed?"

```php
if ($appointment->status !== Appointment::STATUS_CONFIRMED) {
  throw ValidationException::withMessages([
    'status' => "Solo gli appuntamenti confermati possono essere annullati.",
  ]);
}
```

Output escaping answers: "Can user data become HTML?"

Blade's `{{ }}` escapes output by default:

```blade
{{ $appointment->patientName() }}
```

If a malicious patient name contained `<script>`, Blade would display it as text instead of executing it.

Password hashing:

`User` declares:

```php
'password' => 'hashed'
```

So this assignment:

```php
$request->user()->forceFill([
  'password' => $validated['password'],
])->save();
```

stores a hash, not the plain password.

Database consistency:

Transactions protect multi-step changes. In cancellation, the app changes appointment status, frees the slot, and records history inside one transaction. If one part fails, the database should not be left half-updated.

### How To Read A Feature Test

Feature tests simulate user behavior.

Example from booking:

```php
$response = $this->actingAs($patientUser)->post('/appointments', [
  'slot_id' => $slot->id,
  'service_id' => $service->id,
  'notes' => 'Prima visita',
]);

$response->assertRedirect('/patient/appointments');
$this->assertTrue($slot->fresh()->is_booked);
```

Read it as:

1. Pretend we are logged in as this patient.
2. Submit the appointment form.
3. Expect a redirect.
4. Expect the slot to be marked booked in the database.

`RefreshDatabase` resets the database between tests:

```php
use RefreshDatabase;
```

That gives each test a clean database. Tests should not depend on each other.

Tests often create their own data:

```php
$service = MedicalService::create(['name' => 'Visita dermatologica']);
$slot = AvailabilitySlot::create([
  'start_at' => $start,
  'end_at' => $start->addMinutes(30),
]);
```

This is more reliable than depending on seed data.

HTML assertions protect UI contracts:

```php
$response->assertSee('data-comune-combobox', false);
```

The second argument `false` means "do not escape the searched string." That is useful when checking raw HTML attributes.

Database assertions protect persistence:

```php
$this->assertDatabaseHas('appointment_status_history', [
  'appointment_id' => $appointment->id,
  'new_status' => Appointment::STATUS_CANCELLED,
]);
```

This confirms that the app wrote the expected audit row.

### Composer, NPM, And Build Tools

PHP dependencies are managed by Composer:

- `composer.json`: declares dependencies and autoload rules.
- `composer.lock`: exact installed versions.
- `vendor/`: installed PHP packages.

Frontend dependencies are managed by npm:

- `package.json`: declares scripts and JS/CSS dependencies.
- `package-lock.json`: exact installed versions.
- `node_modules/`: installed frontend packages.

Important scripts:

```json
"scripts": {
  "test": [
    "@php vendor/bin/phpunit"
  ]
}
```

So `composer test` runs PHPUnit.

Frontend scripts:

```json
"scripts": {
  "dev": "vite --host 127.0.0.1",
  "build": "vite build"
}
```

So:

- `npm run dev`: starts the development asset server.
- `npm run build`: compiles production assets.

Do not edit `vendor/` or `node_modules/`. They are installed dependencies. Edit your source files and update dependency manifests when needed.

## 18. Mental Model

Think of Laravel as a pipeline plus a set of conventions:

- Routes decide where a request goes.
- Middleware decides whether it is allowed.
- Controllers turn HTTP input into application actions.
- Services enforce business rules that must stay true.
- Models represent database rows and relationships.
- Migrations define the database.
- Blade renders HTML.
- Vite builds CSS and JS.
- Tests describe and protect the behavior.

In this project, the most important invariant is:

> A future available slot can become one confirmed appointment, and any change to that appointment must keep `appointments` and `availability_slots.is_booked` consistent.

That invariant is why `AppointmentService` is the heart of the codebase.
